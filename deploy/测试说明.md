# 第一组自动化测试：Dify 大纲接入

## 1. 为什么需要它

以前运行 `check_outline.py`，是拿一份合法样例检查大纲结构。

本节把真实的 Dify 接入函数 `generate_outline()` 放进自动化测试，检查业务上容易出错的情况。代码修改后，运行同一组测试，及时发现已经修好的问题是否再次出现，这叫回归测试。

这组测试不启动数据库、Dify 或 Ollama，不制作 PPT。它使用固定的 HTTP 模拟响应，调用真实的 `app/clients/dify.py` 代码。

## 2. 如何运行

在 CMD 中执行：

```bat
cd /d D:\project\ppt-agent
deploy\test.cmd
```

脚本调用项目 `.venv` 中的 Python，使用 Python 自带的 `unittest` 执行测试，不需要新增测试依赖。

也可以在 PyCharm 中右键 `backend/tests/test_dify_outline.py`，作为 unittest 运行；解释器应选择项目 `.venv`，并让 `backend` 位于 Python 导入路径。

## 3. 第一组检查什么

| 场景 | 期望行为 |
|---|---|
| 用户需要 6 页，上游返回合法的 6 页 | 接受，并保持 Dify 输入参数约定 |
| 用户需要 6 页，上游返回 7 页 | 拒绝，不能把页数错误的大纲交给后续步骤 |
| cover/content/closing 类型合法，但所在位置错误 | 拒绝 |
| HTTP 为 200，但 Dify 的运行状态是 failed | 按工作流失败处理，保留运行编号 |
| 上游返回截断的 JSON | 转换为可识别的响应错误 |

这里主要验证我们自己的接入和业务判断，不是重复验证 Pydantic 这个库是否实现了字符串长度校验。

## 4. 先理解测试的三步

每项测试都可以按下面的顺序读：

1. **准备条件（Arrange）**：模拟用户需求和 Dify 响应。
2. **执行行为（Act）**：调用真实的 `generate_outline()`。
3. **核对结果（Assert）**：判断结果是否符合预期。

例如：

```python
response = successful_response(7)  # 准备：故意返回 7 页

with self.assertRaises(self.client.DifyOutlineError) as caught:
    self.generate(response)       # 执行：请求仍然要求 6 页

self.assertEqual(caught.exception.code, "DIFY_OUTLINE_INVALID")
```

`assertRaises` 的意思是：这里应该报出指定错误。没有报错，测试反而失败，因为错误大纲被放行了。

## 5. 模拟响应的作用

`httpx.MockTransport` 提供测试响应，实际接入函数依然会完成请求组装、响应解析、页数和顺序检查。

这样测试速度快、结果稳定，不受网络和模型生成随机性影响。测试使用假配置，通过临时替换配置模块加载客户端；不会读取真实 `.env`，替换也会在加载后还原，避免影响其他测试。

模拟不能证明真实 Dify 或 Ollama 当前可用。真实服务连通和完整 PPT 生成仍要通过其他验收检查。

## 6. 怎样读运行结果

- `ok`：这一项结果符合预期，包括“正确地拒绝错误数据”。
- `FAIL`：断言不符合预期，可能是业务行为改变或出现回归。
- `ERROR`：测试执行发生异常，例如缺少依赖、模块无法导入。
- 最后 `Ran 5 tests` 和 `OK`：本组五项检查通过，不代表整个系统所有功能都通过。

发现失败时，先看测试名称和断言，再决定修复代码还是修改需求对应的测试。不要为获得绿色结果而直接删除断言。

## 7. 与项目其他检查的关系

| 检查 | 主要回答的问题 |
|---|---|
| 本组自动化测试 | 给定上游响应时，我们的接入判断是否正确？ |
| 启动检查、健康接口 | 运行环境和相关进程当前是否可用？ |
| 提交任务并下载 PPT | 完整业务流程能否完成？ |
| 备份恢复演练 | 保存的数据和配置能否恢复使用？ |

后续再逐步扩展权限隔离、幂等提交、Worker 租约等关键测试，并接入提交代码时自动运行的 CI。
