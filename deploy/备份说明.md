# 本机数据备份：先学会可靠执行，再扩展保存位置

## 1. 这次做了什么

把已经手动完成的“暂停写入 → 导出数据库 → 复制 PPT → 恢复服务”整理成可重复执行的工具。

- `backup.cmd`：Windows 上的入口，负责找项目目录、使用项目 Python、保留结果窗口。
- `backup.py`：实际的流程控制，使用 Python 标准库调用现有 Docker Compose 命令。
- `backups/data-日期-时间-随机编号/`：每次一个新目录，避免覆盖上次备份。

没有增加 Python 依赖，也不需要重建容器镜像。两个脚本在 Windows 主机上运行。

## 2. 先检查，再正式备份

在 CMD 中进入项目目录：

```bat
cd /d D:\project\ppt-agent
deploy\backup.cmd --check-only
```

此模式检查 Compose 配置、三个现有容器的状态、数据库连接和是否有未完成任务。它不暂停服务，不导出数据，也不检查所有文件是否完整；这些在正式备份期间执行。

成功输出：

```text
[PASS] Preflight passed. No services stopped; no backup created.
```

等所有排队和制作中的任务结束，正式备份：

```bat
deploy\backup.cmd
```

也可以双击 `backup.cmd` 正式备份。不要同时运行另一份备份、启动脚本或手动启停容器。

备份期间 API 和 Worker 会短暂停止，网页暂时无法办理业务。PostgreSQL 和前端容器不停止。

## 3. 程序怎样完成备份

1. 建立 `.backup.lock`，阻止两个备份进程互相干扰。
2. 检查容器和数据库；如果有 queued/planning/rendering/checking 任务，退出并请你稍后再试。
3. 记录 API、Worker 原来是否运行。
4. 停止运行中的 API，再查一次任务，防止刚好有人在暂停前提交。
5. 确认没有未完成任务，再停止运行中的 Worker。
6. 将 `pg_dump -Fc` 的二进制输出直接写入新目录的 `database.dump`。
7. 用 `pg_restore --file=/dev/null` 读取全部归档内容，但不连接数据库恢复。
8. 复制 storage，比较每份源文件和副本的 SHA-256。校验值可以理解为文件内容的“指纹”。
9. 核对每一条 succeeded 任务的 artifact_path，都能在复制的文件中找到。
10. 无论复制成功还是普通错误，都在 `finally` 中尝试恢复本次停止的服务；原来停止的服务保持停止。
11. 服务恢复通过健康检查后，写清单，将目录从 `.incomplete` 改名，最后才显示 PASS。

这体现三个开发思想：

- **先检查条件再执行操作**：忙碌时退出，避免打断任务。
- **资源清理放在 finally**：发生错误也有机会恢复服务。
- **按证据报告成功**：命令成功、文件核对通过、服务恢复后，才显示成功。

## 4. 输出内容

```text
backups/
└─ data-20261020-153000-随机编号/
   ├─ database.dump
   ├─ manifest.json
   └─ storage/
      └─ 任务编号/执行编号/presentation.pptx
```

`manifest.json` 是备份清单，包含时间、任务数、文件路径、大小、SHA-256、服务恢复结果。它不复制 `.env` 或 API Key。

`restore_tested: false` 是有意保留的：读取归档、核对文件，不等于已经在一个新数据库中恢复成功。恢复演练之后才能单独记录这项证据。

## 5. 出错时怎样处理

- 有未完成任务：等它们完成，再运行；这个检查不会停止容器。
- 停 API 后出现未完成任务：脚本恢复 API 并退出，稍后再试。
- 数据导出、复制、文件关联检查失败：保留 `.incomplete` 目录，不会用它替代旧备份。读屏幕错误，不要直接当作成功备份。
- 某条成功任务对应的文件已丢失：这说明现有数据就缺文件，需要定位并修复，不能让脚本假报成功。
- 服务恢复失败：运行 `deploy\start.cmd`，再检查日志。脚本不会把“数据复制好了但服务没有恢复”显示成完全成功。
- Docker 命令失败只显示操作类别和退出码，避免配置值被打印出来。结合 `docker compose ... ps` 和受影响服务日志继续定位。
- 强制结束进程、关闭电脑、断电不能保证 finally 执行。恢复后先运行 `deploy\start.cmd`。若出现锁文件提示，确认备份进程已结束，再手动移除 `backups\.backup.lock`；不要删除其他备份目录。

脚本没有自动删除旧备份。定期留意 D 盘空间。

## 6. 明确保护范围

这是**当前项目单机 Compose 环境的数据备份**：

- 包含 `ppt_agent` 数据库结构、数据，以及 `backend/storage` 文件。
- 暂停的是本 Compose 管理的 API/Worker。请先关闭另外运行的 PyCharm API/Worker，也不要同时人工修改数据库或 storage。
- 依赖现有数据库账号和 PostgreSQL 容器；数据库角色定义、密码、部署配置、Dify 工作流和 Ollama 模型不在本备份范围。
- 同 D 盘保存能帮助应对误删、错误修改和部分恢复场景，不能应对整块磁盘损坏。
- `backups/` 已在 `.gitignore` 中，应继续保持忽略。数据库备份本身包含用户、会话和业务信息，不要公开上传。
- 这不是不停机备份，也不是整机灾难恢复方案。当前采用短维护窗口，是为了把数据一致性和恢复流程先学清楚。

## 7. 后续学习顺序

先在真正 Docker 环境运行检查和一次正式备份，然后用这次新目录进行独立数据库恢复演练。再补齐部署/工作流恢复说明、独立存储副本、保留策略和定时任务。
