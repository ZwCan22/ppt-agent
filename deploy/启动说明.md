# PPT 项目的统一启动入口

## 使用方法

先打开 Docker Desktop，按现有方式启动 Dify 和本机 Ollama。
然后双击本目录的 start.cmd，或在项目根目录 CMD 中执行：

```cmd
deploy\start.cmd
```

出现以下标志表示四个 PPT 服务以及本脚本定义的启动检查通过：

```text
[PASS] Four PPT services and startup checks passed.
```

随后打开 http://127.0.0.1:18080/。
窗口停留是为了方便阅读结果；按任意键结束脚本，后台服务会继续运行。

## 按顺序做了什么

1. 检查环境文件存在、Docker Engine/Compose 可用、Compose 配置能解析，
   以及前后端镜像标签已存在。配置检查使用 --quiet，避免显示展开后的密码。
2. 启动 PostgreSQL 与 API，等待它们的健康检查通过，最多等待 90 秒。
3. 用临时容器运行 worker_preflight.py：只读查询数据库身份、访问 Dify 应用
   信息接口，并检查 PPT 和日志目录的读写权限。临时探针文件随后删除。
4. 启动 postgres、api、worker、frontend 四个服务，并等待健康检查通过。
   这样 Worker 会明确纳入启动范围。
5. 通过用户访问的前端地址检查 /api/health/db 和 /api/health/worker。
   验证前端 Nginx 能转发到 API，以及 API 能读取数据库和 Worker 存活心跳。

## 为什么分阶段

先准备依赖，再验证 Worker 环境，最后启动全部服务。每一步失败即停止后续步骤，
避免把中间失败显示为整体启动成功。已有容器会保留，方便查看失败现场。
如果 Worker 本来已运行，脚本不会先停掉它，因此预检查失败也不意味着已有
Worker 被暂停。脚本用于日常启动检查，不是运行期间的故障隔离器。

## 它证明了什么

- 数据库、API、Worker 和前端已通过各自健康检查。
- Dify Workflow 应用信息可访问，API Key 能通过该接口验证。
- 当前 Worker 用户能读写 PPT 和日志目录。
- 从前端入口能够访问数据库检查和 Worker 心跳检查。

这不能证明模型推理成功，也不能证明业务线程一直在推进。Dify 应用信息接口
正常时，Ollama 仍可能不可达。使用实际 PPT 任务验证完整业务链路。
运行期间的排队积压监控与通知属于后续步骤。

## 日常启动与版本更新

start.cmd 使用已经构建好的 ppt-agent-backend:dev 与 ppt-agent-frontend:dev。
更新源码后，先按本节前面的说明构建对应镜像，再使用启动入口。
Compose 发现镜像或服务配置变化时可能重建容器，因此更新前等待当前任务完成。
数据卷不会因为重新执行本脚本而被删除。

本入口负责 PPT 项目的四个服务；Dify 与本机 Ollama 使用各自现有的启动方式。
脚本中的前端端口为本项目当前约定的 18080。变更端口时需要同时调整入口检查。

## 当前验证范围

已检查脚本的参数、阶段顺序、错误退出路径、CRLF/ASCII 编码和路径引用，
并与实际 Compose 服务及前端入口配置核对。本工具无法执行 Docker 引擎操作，
实际服务启动与脚本运行需在用户本机验收。

通过真实 Docker 执行后，再以最终 PASS 和页面访问结果作为验收依据。
脚本始终在原窗口等待按键，便于双击运行时查看报错。
