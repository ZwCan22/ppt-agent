# PPT Agent 交付与维护

## 1. 目标与依赖

交付 Windows 本机 Docker 教学与内部验证版本。依赖 Python 3.13、Node.js 24、PostgreSQL 17、Docker Desktop、独立 Dify 和可用模型服务。本机 Ollama 继续使用已有安装。命令使用 CMD，从项目根目录开始。

## 2. 首次部署

### 源码与依赖

获取审核通过的代码，记录 `git rev-parse HEAD`，然后：

```bat
py -3.13 -m venv .venv
.venv\Scripts\python.exe -m pip install --only-binary=:all: -r backend\requirements.lock.txt
cd frontend
npm ci --no-audit --no-fund
cd ..
```

使用 Anaconda 时可通过 PyCharm 对应 3.13 解释器创建 .venv。锁文件用于复现依赖，requirements.in 表达直接依赖意图。

### 配置

```bat
if not exist backend\.env copy backend\.env.example backend\.env
if not exist deploy\.env copy deploy\.env.example deploy\.env
```

在 PyCharm 填写 deploy/.env 的 POSTGRES_PASSWORD（ppt_admin 管理密码），backend/.env 的 PPT_DB_PASSWORD（ppt_app 业务密码）和 PPT_DIFY_API_KEY（已发布工作流 Key）。两种数据库账号使用各自密码。

在 Dify 导入并发布经过验证的 PPT 工作流；输入 topic、audience、slide_count、requirements，输出 outline。DSL 与凭证单独保管；仓库不包含你的 Dify 应用或 Key。

后端本机 Dify 地址 http://localhost/v1；Compose 覆盖为 http://host.docker.internal/v1。Dify 自己配置到模型的连接，Worker 能访问 Dify 不代表 Dify 能访问 Ollama。

### 初始化数据库（仅首次）

```bat
docker compose --env-file deploy\.env -f deploy\compose.yml up -d --wait postgres
docker compose --env-file deploy\.env -f deploy\compose.yml exec postgres psql -U ppt_admin -d ppt_agent
```

在 psql 中，仅当角色尚不存在时执行：

```sql
CREATE ROLE ppt_app LOGIN;
\password ppt_app
\q
```

业务密码与 backend/.env 一致。再在项目根目录 CMD 执行：

```bat
docker compose --env-file deploy\.env -f deploy\compose.yml exec -T postgres psql -U ppt_admin -d ppt_agent < backend\migrations\bootstrap.sql
cd backend
..\.venv\Scripts\python.exe -m alembic upgrade head
..\.venv\Scripts\python.exe -m alembic current
cd ..
```

Alembic 交互要求 ppt_admin 密码；当前 head 为 0007，后续以实际版本为准。业务账号仅读写业务表，无建表和迁移 Schema 权限。

### 构建与启动

```bat
if not exist backend\storage mkdir backend\storage
docker build -t ppt-agent-backend:dev backend
docker build -t ppt-agent-frontend:dev frontend
deploy\start.cmd
```

打开 http://127.0.0.1:18080/，通过页面注册并登录，不分发固定业务账号。

## 3. 验收

执行 deploy/test-all.cmd。还应创建一份真实 6 至 8 页 PPT，确认任务完成、文件下载、中文字体、页数、内容与排版。轮询不一定能看到每个短暂中间状态。

自动测试不调用模型，不能代替真实业务验收。当前端口绑定本机，Compose 使用 development Cookie 配置。

## 4. 日常排错

```bat
docker compose --env-file deploy\.env -f deploy\compose.yml ps
docker compose --env-file deploy\.env -f deploy\compose.yml logs --tail=100 worker
```

| 现象 | 检查 |
|---|---|
| 页面打不开 | frontend 与 /healthz |
| 数据库暂时不可用 | /api/health/db、postgres、业务账号配置 |
| 一直 queued | /api/health/worker、/api/health/queue、Worker 是否启动 |
| planning 失败 | Worker 的 task_id、error_code、dify_run_id，再查 Dify 对应运行 |
| Dify 通但模型失败 | Dify 到 Ollama 的地址、监听、代理 |
| 成功却不能下载 | 当前用户、artifact_path、API/Worker 是否共享 storage |

Worker 心跳只证明进程报告存活，不保证模型推进。日志按编号定位，避免粘贴 .env、Cookie 和私密需求。

## 5. 备份与恢复

执行 deploy/backup.cmd，确认 status=completed、服务已恢复。保留同一备份中的 database.dump、storage、manifest.json，另保管匹配的配置、Dify DSL 和代码版本。

自动备份不包含数据库角色密码、Dify 平台数据库和 Ollama 模型。恢复新环境要先准备这些依赖。

先恢复到新数据库检查数量、迁移版本，并打开对应 PPT；通过后安排业务切换。恢复演练与业务切换是两个步骤。详细命令见备份说明。

目前 D 盘副本不覆盖该物理盘损坏；成功备份应另存独立设备或外部存储，并记录恢复验收。

## 6. 更新与回退

1. 等待在途任务完成、队列清空，做配对备份并记录代码提交。
2. 给当前镜像加 before-upgrade 等版本标签，保留旧镜像。
3. 停止 api 和 worker，避免更新中接受或处理任务。
4. 更新到审核通过的代码、安装对应锁文件、执行 Alembic upgrade head。
5. 重新构建镜像，运行 start.cmd，检查健康与真实 PPT。
6. 记录提交、迁移版本、备份目录和验收结果。

仅代码变化且数据库兼容时可恢复旧镜像和匹配配置。数据库变化先评估兼容性，优先在新库验证配对备份再安排切换。自动测试中的 downgrade 只针对空临时测试库，不能照搬到业务库。

## 7. 公网发布前的独立验收

确定域名、HTTPS、反向代理与密钥存储；配置 production 和 Secure Cookie，验证登录与跨站请求边界；按预期人数、GPU 和任务时长做容量测试，确定限流与排队策略；准备外部备份及告警接收人。

本轮没有执行公网发布或重建运行中的业务容器。交付内容为本机可维护版本、自动检查和运维流程。
